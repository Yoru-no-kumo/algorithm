# メモリ構造

## 1. メモリ構造とは

メモリ構造とは、実行中のプログラムが使用するメモリスペースが役割、寿命、管理方式に対して分かれる配置を指します。

一般的に次の様相が含まれています。

- Text/Code 領域: 実行する機械語（または、VMバイトコード）は位置
- Data 領域: グローバル・静的データ（初期化の有無により .data/.bss）定数等
- Heap 領域: 動的に割り当てられたオブジェクトは保存される領域。寿命はコード構造だけでは固定されない（GCの対象）
- Stack 領域: 関数/メソッド呼び出しで生成される呼び出しフレーム（引数。ローカル変数・リターンアドレス等）。LIFOで自動解放

> JVM環境では、OS寒天の上記に加え、Java Heap/Thread Stacks/Metaspace/Code Cache/String Intern Poolといったランタイム上の理論区画は存在します。

## 2. メモリ構造の形態

### 概念

- Thread Stack: スレッドごとに存在。メソッド呼び出し時にスタックフレーム生成（ローカル・引数・リターンアドレス・一部の一時値）。メソッド終了で自動解放。GCの対象外
- Heap (Java Heap): `new`で生成されたオブジェクト/配列は保存。GCの主要対象
- Metaspace: クラスメタデータ（メソッド/フィールドシグネチャ、継承情報、定数プール構造、メソッドのバイトコード参照等）を保存
- Code Cache: JITコンパイラがホットなメソッドをネイティブ機械語にコンパイルして格納する領域
- String Intern Pool: Javaは文字列リテラルや`String.intern()`の結果を保存（ヒープ内の特別な領域として捉えると安全）。不変（Immutable）で再利用される。

### 図

``` text
# Javaの場合
┌──────────────────────────────────────────────────────────┐
│                OS / Runtime (共有ライブラリ等)            │
├──────────────────────────────────────────────────────────┤
│ [Code Cache]           ← JITが生成したネイティブ機械語     │
├──────────────────────────────────────────────────────────┤
│ [Metaspace]           ←   クラスメタデータ                │
│                           定数プール構造                  │
│                           メソッドのバイトコード参照等     │
├──────────────────────────────────────────────────────────┤
│ [Java Heap]                                              │
│   • 객체/배열 (new)                                       │
│   • String Intern Pool ("...")                           │
│   • Class Mirror (java.lang.Class<...>)                  │
├──────────────────────────────────────────────────────────┤
│ [Thread Stacks]   ←   スレッドごとのスタックフレーム        │
│                       (ロカール/パラメータ)                │
└──────────────────────────────────────────────────────────┘
```

正確性チェック

- スタックはメソッド・関数終了で自動解放 → GC対象外
- ヒープのオブジェクトは到達可能性に基づきGCが回収
- クラスメタデータ（及びバイトコード参照）はMetaspace
- JITでネイティブ化されたコード(機械語)はCode Cache
- 文字列リテラル/`String.intern()`はIntern Pool(ヒープ)

### Java例示コード

次の簡単な例でロード/配置を追いかけます。

``` java
public class Hello {
    static final int CONST = 42;        // コンパイル時定数（異様箇所で inlining）
    static String msg = "hi";           // 静的フィールド（参照）。 "hi"はIntern Pool対象
    private int n;                      // インスタンスフィールド
    public Hello(int n) {               // <init> バイトコード
        this.n = n;
    }
    public int add(int x) {             // インスタンスメソッド
        return n + x;
    }
    public static int twice(int x) {    // 性的メソッド
        return x * 2;
    }
    public static void main(String[] args) {
        Hello h = new Hello(10);
        System.out.println(h.add(5));
        System.out.println(twice(CONST));
        System.out.println(msg);
    }
}
```

### ロード・配置の流れ（HotSpot）

- クラスローディング時
  - Hello クラスのメタデータ（フィールド/メソッドシグネチャ、継承情報、定数プール構造 等）が Metaspace に配置。
  - 各メソッドのバイトコードはメタデータから参照される形で管理（インタプリタが実行、ホット化すれば JIT）。
  - 文字列リテラル "hi" は String Intern Pool（ヒープ） に保存（既存なら再利用）。
  - static フィールドの「保存実体」は ヒープ側（Class Mirror 等） が保持すると理解すると安全（メタデータとヒープの境界はあるが、値自体はヒープ側で管理）。
  - static final int CONST = 42 はコンパイル時定数として、使用箇所でinliningされ、バイトコードに即値として埋め込まれる（別途のランタイム保存は不要）。

- 実行中
  - new Hello(10) → ヒープにインスタンス { n:10 } を生成。ローカル変数 h は スタックに参照値を保存。
  - add(5) 呼び出し → スタックフレームに this・x 等のローカルが生成。n はヒープ上のインスタンスからロード。
  - 頻繁に呼ばれてホット化すると、add / twice 等のメソッドは JIT コンパイルされ Code Cache に機械語として保存。その後はネイティブ経路で高速実行。

#### 図

``` text
┌──────────────────────────────────────────────────────────────┐
│ [Code Cache]  ← ホットなメソッドのネイティブコード（JIT）       │
│   • Hello.add(int), Hello.twice(int)（ホット化でコンパイル）   │
├──────────────────────────────────────────────────────────────┤
│ [Metaspace]   ← クラス/メソッドのメタデータ、定数プール構造      │
│   • Class Hello（フィールド/メソッドシグネチャ、継承、vtable 等）│
│   • 各メソッドのバイトコード参照（<init>, add, twice, main）    │
│   • "hi" のシンボル情報 等（実体は Intern Pool）               │
├──────────────────────────────────────────────────────────────┤
│ [Java Heap]                                                  │
│   • String Intern Pool : "hi"                                │
│   • Class Mirror<Hello> : static フィールドの実体（msg 参照 等）│
│     - CONST=42 は使用箇所で inlining され別保存は不要           │
│   • インスタンス: new Hello(10) → { n=10 }                    │
├──────────────────────────────────────────────────────────────┤
│ [Thread Stack: main]                                         │
│   • h（参照）→ ヒープ上の Hello インスタンス                    │
│   • 呼び出しフレームの push/pop（引数/ローカル/リターンアドレス） │
└──────────────────────────────────────────────────────────────┘
```

#### ダブルチェック要点

- static final プリミティブ定数は使用箇所で inlining → ランタイム保存最小化
- 文字列リテラルは Intern Pool（ヒープ）
- static 参照フィールドの保存実体は ヒープ（Class Mirror 等）
- メソッドバイトコードは Metaspace が管理/参照、JIT ネイティブコードは Code Cache
- ローカル変数/引数は スタックフレーム

## 3. スタックとヒープとは？

### Stack

- メソッド呼び出しでフレーム生成（引数・ローカル・リターンアドレス・一時値の一部はレジスタ）。
- LIFOで自動割当/解放。
- ローカルの寿命はブロック/メソッド終了に連動。
- GC 非対象（フレームpopで自動消滅）。
- 非常に高速でキャッシュ親和性が高い。

### Heap

- new 等で動的割当されたオブジェクト/配列を格納。
- 寿命はコード構造に固定されない（多様な参照で生存しうる）。
- 参照が切れれば GC が回収（Tracing/Generationalなど）。
- ポインタ間接参照が必要になりStackより相対的に高コスト。

## 4. スタックとヒープの比較

|項目|Stack|Heap|
|------|------|------|
|役割|呼び出しフレーム（ローカル/引数/リターンアドレス）|動的オブジェクト/配列の格納|
|s寿命|関数/ブロック終了で自動消滅|参照が切れるまで（GC が回収）|
|管理主体|コンパイラ/ランタイム（自動）|ランタイム（GC）|
|速度/アクセス|非常に速い・連続メモリ|相対的に遅い・間接参照|
|リスク/論点|スタックオーバーフロー（深い再帰/巨大ローカル配列）|メモリリーク（参照残存）、断片化|
|GC対象|×|〇|

## 5. プリミティブ型と参照型：宣言・割当時に「データ領域」にどう保存されるか

### プリミティブ（Primitive）

- 例：int, long, double, boolean など
- ローカル変数/引数 → スタックフレームに値そのものを保存
- フィールド（インスタンス/静的） → そのフィールドを持つオブジェクト（または Class Mirror）のメモリレイアウトに値として保存（ヒープ）

#### 例

``` java
int a = 10;             // a はスタック（値 = 10）
class C { int v = 1; }  // new C() のヒープオブジェクト内部レイアウトに v（値 = 1）を保存
```

- ローカル a は スタック上の値。
- C.v は ヒープ上のオブジェクト内部フィールド（値として格納）

### 参照型（Reference）

- 例：String, Object, int[], 自作クラス など
- ローカル変数/引数 → スタックには参照値（アドレス）、実体はヒープ
- フィールド（インスタンス/静的） → フィールドスロットに参照値を保存、実体オブジェクトはヒープ

#### Javaの参照型例

``` java
String s = "hi";           // s：スタックの参照値、"hi"：Intern Pool（ヒープ）
int[] arr = new int[2];    // arr：スタックの参照、配列の実体：ヒープ
C obj = new C();           // obj：スタックの参照、C インスタンス：ヒープ
```

#### static final プリミティブ定数

``` java
static final int CONST = 42;
System.out.println(CONST); // バイトコードでは即値として直接使用（inlining）
```

- 使用箇所で 42 が直接入る → 別途ヒープ/スタックに保存する必要なし（必要ならローカルにロード）

#### static 参照フィールド

``` java
static String msg = "hi";  // msg の保存実体はヒープ（Class Mirror 等）、"hi" は Intern Pool（ヒープ）
```

#### 正確性再確認

- ローカルプリミティブ値はスタック（フィールドなら、そのオブジェクト/クラスのヒープ側レイアウト）
- ローカル参照型変数はスタックに参照値、実体はヒープ
- 文字列リテラルは Intern Pool（ヒープ）
- 静的フィールドの保存実体はヒープ（Class Mirror 等）
- コンパイル時プリミティブ定数は使用箇所 inlining

## 6. まとめ

- Stack: 呼び出しフレーム（ローカル/引数）。自動解放。GC対象外。
- Heap: 動的オブジェクト/配列。参照が切れれば GCが回収。
- Metaspace: クラスメタデータ/定数プール構造/メソッドのバイトコード参照。
- Code Cache: JITにより生成されたネイティブコード。
- String Intern Pool: 文字列リテラル/`intern()`の結果（ヒープ）。
- Java において
  - ローカルのプリミティブ: スタック上の値、フィールドのプリミティブ : 当該オブジェクト/クラスのヒープ側レイアウト
  - ローカルの参照型: スタックの参照値、実体はヒープ
  - static final のプリミティブ定数: 使用箇所でinlining
  - static 参照フィールド: ヒープ（Class Mirror等）に保存、リテラルはIntern Pool
